SAST, DAST y SCA

Las tres maneras de análisis automático de seguridad de aplicaciones. Cada una apunta a una parte distinta.

1. SAST (Static Application Security Testing — Pruebas Estáticas)

¿Qué es? Esencialmente, es como tener un revisor automático que lee el código fuente (sin ejecutarlo) buscando fallas de seguridad, malas prácticas o errores de sintaxis que puedan convertirse en vulnerabilidades (como contraseñas hardcodeadas o vulnerabilidades lógicas).

Cuándo se usa: muy temprano en el desarrollo, a menudo directamente en el editor de código o justo al hacer un commit.

Herramientas populares:

  • SonarQube / SonarCloud — descargar SonarQube · SonarCloud (en la nube, sin descarga)
  • Semgrep — instalar · GitHub
  • Checkmarx — web oficial (de pago, sin descarga libre)
  • GitHub Advanced Security (CodeQL) — descargar CodeQL CLI · documentación

2. SCA (Software Composition Analysis — Análisis de Composición de Software)

¿Qué es? Las aplicaciones modernas no se escriben desde cero; utilizan cientos de librerías, paquetes y dependencias de terceros (como módulos de npm, paquetes de PyPI, etc.). El SCA escanea todas estas dependencias externas para avisarte si estás usando alguna versión que tenga vulnerabilidades públicas conocidas (CVEs).

Cuándo se usa: durante la gestión de dependencias y en la integración continua (CI/CD).

Herramientas populares:

  • Snyk — instalar Snyk CLI
  • OWASP Dependency-Check — descargar · web oficial
  • GitHub Dependabot — cómo activarlo (no se descarga, viene en GitHub)
  • Trivy — descargar

3. DAST (Dynamic Application Security Testing — Pruebas Dinámicas)

¿Qué es? A diferencia de SAST, el DAST analiza la aplicación mientras está en ejecución. Simula ataques externos (como inyecciones SQL o ataques de fuerza bruta) desde el punto de vista de un hacker real para ver cómo reacciona el sistema desplegado en un entorno de pruebas.

Cuándo se usa: en etapas más avanzadas del pipeline, cuando la aplicación ya está corriendo en un entorno de pruebas o pre-producción.

Herramientas populares:

  • OWASP ZAP (Zed Attack Proxy) — descargar
  • Burp Suite (versión Enterprise / Automated) — web de la versión Enterprise (de pago) · descargar Community (gratis)
  • Nuclei — descargar

En detalle

SAST — análisis estático

Lee el código sin ejecutarlo y busca patrones peligrosos: datos que llegan del usuario y terminan en una consulta SQL sin sanitizar, claves API escritas en el fuente, uso de funciones criptográficas obsoletas. Corre rápido y temprano, así que va en el pipeline del Pull Request. Su punto débil son los falsos positivos: sin ajustar las reglas, genera mucho ruido y el equipo lo empieza a ignorar. No entiende la configuración de runtime ni si una ruta vulnerable es realmente alcanzable.

DAST — análisis dinámico

Ataca la aplicación mientras corre, mandándole peticiones maliciosas como haría un atacante externo. Encuentra cosas que solo se ven en ejecución: cabeceras de seguridad faltantes, cookies sin HttpOnly, TLS mal configurado, XSS reflejado. Necesita un entorno desplegado, es más lento y no te dice la línea de código que hay que tocar, solo la URL y el síntoma. Por eso suele correr contra staging, de noche o antes de un deploy. Importante: correr un DAST contra un sistema que no es tuyo, sin autorización por escrito, es un ataque.

SCA — análisis de dependencias

Mira las librerías de terceros que usa el proyecto y las cruza con bases de vulnerabilidades conocidas (CVE, avisos de GitHub). El código propio suele ser una fracción de lo que se despliega; el resto son dependencias, y ahí es donde entran la mayoría de los problemas hoy. También revisa las licencias y genera el SBOM (Software Bill of Materials): la lista completa y versionada de todo lo que compone el build, útil para responder "¿me afecta esta CVE nueva?" en minutos.

Cómo se combinan en un pipeline

  • En el Pull Request: SCA y SAST, que son rápidos. Si aparece algo de severidad alta, el pipeline falla y bloquea el merge.
  • Contra staging: DAST, más lento, en un job nocturno o previo al deploy.
  • Triage: no trates todo hallazgo como crítico. Priorizá por severidad y por probabilidad real de explotación (CVSS para el impacto, EPSS para la probabilidad).

El ejemplo de pipeline en el overview ya mete un SCA (Snyk) y un SAST (ESLint con reglas de seguridad) en el workflow del Pull Request.

Errores comunes

  • Correr las herramientas con la configuración por defecto y no ajustar las reglas: el ruido entierra los hallazgos reales.
  • No versionar la configuración del escáner junto al código.
  • Silenciar un hallazgo sin dejar escrito por qué (mejor una supresión con justificación y fecha de revisión que un "ignorar" a ciegas).
  • Tratar el número de hallazgos como métrica de éxito en vez de mirar cuáles se arreglaron.
  • Lanzar un DAST sobre entornos de producción o de terceros sin autorización.
