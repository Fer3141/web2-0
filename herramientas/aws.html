AWS

Amazon Web Services es la nube de Amazon: en vez de comprar servidores, alquilás cómputo, almacenamiento, bases de datos y cientos de servicios más, y pagás por lo que usás (pay-as-you-go). Esta página es un mapa de lo que conviene aprender y en qué orden. Cada servicio enlaza a su documentación oficial.

Qué es AWS

La nube se suele dividir en tres modelos según cuánto gestiona el proveedor:

Modelo Vos gestionás Ejemplo en AWS
IaaS (infraestructura) SO, runtime, tu app EC2 (una máquina virtual)
PaaS (plataforma) Solo tu app y su config Elastic Beanstalk, App Runner, RDS
Serverless / FaaS Solo el código de una función Lambda, S3, DynamoDB, SQS

Modelo de responsabilidad compartida: AWS asegura la nube (hardware, red física, hipervisor); vos asegurás lo que ponés en la nube (tus datos, permisos IAM, parches del SO si usás EC2, configuración de los servicios).

1. Crear la cuenta y no gastar de más

  • Registrate en aws.amazon.com/free. Pide tarjeta pero hay una capa gratuita: algunos servicios gratis siempre, otros 12 meses, otros como prueba puntual.
  • Lo primero, antes de tocar nada:
    • Activá MFA en la cuenta root.
    • No uses la cuenta root para el día a día: creá un usuario IAM (o mejor, IAM Identity Center) con permisos de admin.
    • Poné un AWS Budget con alerta por correo a USD 1 y otro a USD 10.
    • Activá las alertas de facturación en CloudWatch.
  • Reglas para no llevarte una sorpresa: apagá o borrá lo que no uses (sobre todo EC2, NAT Gateway, bases RDS, IPs elásticas sin asociar, balanceadores), y trabajá siempre en una sola región.

2. Regiones y zonas de disponibilidad

  • Una Región es un conjunto de centros de datos en una zona geográfica (p. ej. us-east-1 en Virginia, sa-east-1 en São Paulo). Elegís según cercanía a los usuarios, precio y qué servicios hay disponibles.
  • Cada región tiene varias Zonas de Disponibilidad (AZ): centros de datos aislados entre sí pero conectados con baja latencia. Repartir tu app en 2–3 AZ es lo que le da tolerancia a fallos.
  • Edge locations: cientos de puntos de presencia que usan CloudFront y Route 53 para acercar el contenido al usuario.
  • Servicios globales (no viven en una región): IAM, Route 53, CloudFront, WAF.

3. Consola, CLI y SDK

  • Consola web: para explorar y aprender. No para cosas repetibles.
  • AWS CLI: instalás, corrés aws configure (o mejor aws configure sso) y ya podés scriptear todo.
  • SDK: librerías para cada lenguaje (boto3 en Python, aws-sdk en JS, etc.) para hablar con AWS desde tu código.
  • CloudShell: una terminal con la CLI ya configurada, dentro de la consola.
aws configure sso # login moderno con IAM Identity Center aws sts get-caller-identity # ¿quién soy? útil para verificar credenciales aws s3 ls # lista tus buckets

4. IAM: identidad y permisos

IAM (Identity and Access Management) controla quién puede hacer qué sobre qué recurso. Es lo más importante de AWS y lo más fácil de hacer mal.

Concepto Qué es
Usuario Una identidad permanente para una persona o una app (evitá las claves de acceso largas).
Grupo Un conjunto de usuarios al que se le adjuntan políticas.
Rol Identidad temporal que asume un servicio (p. ej. una EC2) o un usuario. La forma correcta de dar permisos a aplicaciones.
Política Documento JSON con Effect (Allow/Deny), Action, Resource y Condition.
IAM Identity Center El sucesor de los usuarios IAM para personas: login único, credenciales temporales, integra con tu proveedor de identidad.

Buenas prácticas:

  • Mínimo privilegio: empezá sin permisos y agregá solo lo que haga falta.
  • Roles en vez de claves de acceso siempre que se pueda.
  • MFA para todo lo humano.
  • Nada de credenciales en el código: usá roles, o Secrets Manager.
  • Revisá con IAM Access Analyzer qué recursos quedaron expuestos.
{ "Version": "2012-10-17", "Statement": [{ "Effect": "Allow", "Action": ["s3:GetObject"], "Resource": "arn:aws:s3:::mi-bucket/*" }] }

5. Red: VPC y compañía

La VPC (Virtual Private Cloud) es tu red privada dentro de AWS. Casi todo lo demás vive dentro de una.

  • Subredes: trozos de la VPC atados a una AZ. Públicas (con ruta a internet) o privadas.
  • Internet Gateway: la puerta a internet de las subredes públicas.
  • NAT Gateway: deja que las subredes privadas salgan a internet sin ser alcanzables desde afuera. Cuesta plata por hora y por tráfico — ojo con esto.
  • Route tables: a dónde va cada paquete.
  • Security Groups: firewall con estado a nivel de recurso (p. ej. una EC2). Solo reglas de permitir.
  • Network ACL: firewall sin estado a nivel de subred. Permitir y denegar.
  • Elastic Load Balancing: reparte tráfico (ALB para HTTP, NLB para TCP).
  • Route 53: DNS gestionado + chequeos de salud + enrutamiento por latencia/geografía.
  • CloudFront: CDN; cachea contenido cerca del usuario.

6. Cómputo

Servicio Cuándo usarlo
EC2 Máquinas virtuales. Control total, vos parcheás el SO. Tipos de instancia según CPU/RAM/red; opciones de compra: On-Demand, Savings Plans, Spot (barato pero te la pueden quitar).
Auto Scaling Group Subir y bajar la cantidad de EC2 según demanda o salud.
Lambda Ejecutar una función ante un evento (HTTP vía API Gateway, archivo nuevo en S3, mensaje en cola). Sin servidores que gestionar, pagás por invocación y milisegundos.
App Runner / Elastic Beanstalk Subir una app web y que AWS se encargue de servidores, balanceo y escalado.

7. Almacenamiento

Servicio Tipo Para qué
S3 Objetos Archivos, backups, hosting estático, data lakes. Clases de almacenamiento (Standard, Infrequent Access, Glacier) según cuánto lo consultás. Por defecto todo privado: cuidá no abrir un bucket sin querer.
EBS Bloque El "disco duro" de una EC2. Vive en una AZ. Hacé snapshots para backup.
EFS Archivos (NFS) Un sistema de archivos compartido entre varias EC2 a la vez.

8. Bases de datos

Servicio Qué es
RDS Bases relacionales gestionadas: PostgreSQL, MySQL, MariaDB, SQL Server, Oracle. AWS hace backups, parches y réplicas. Multi-AZ para alta disponibilidad.
Aurora Versión de AWS de MySQL/PostgreSQL, más rápida y con opción serverless.
DynamoDB NoSQL clave-valor totalmente gestionada, escala sola, latencia de milisegundos. Muy usada con Lambda.
ElastiCache Redis o Memcached gestionado, para cachear y bajar carga de la base.

9. Contenedores y serverless

  • ECR: registro privado de imágenes Docker (ver Docker).
  • ECS: orquestador propio de AWS, más simple que Kubernetes.
  • EKS: Kubernetes gestionado, si ya sabés Kubernetes o necesitás su ecosistema.
  • Fargate: corré contenedores en ECS o EKS sin gestionar las EC2 de abajo.
  • Serverless típico: API Gateway + Lambda + DynamoDB, con SQS/SNS/EventBridge para eventos y colas.

10. Infraestructura como código

No crees recursos a mano en la consola para nada que quieras conservar. Descríbelos en archivos versionados (ver también IaC en DevSecOps).

  • CloudFormation: el servicio nativo. Plantillas YAML/JSON; AWS gestiona el estado.
  • AWS CDK: defines la infra en un lenguaje de verdad (TypeScript, Python...) y compila a CloudFormation.
  • Terraform: multi-nube, el más pedido en ofertas. Tiene su certificación Associate.
  • AWS SAM: CloudFormation simplificado para serverless.

11. CI/CD en AWS

Podés usar Jenkins o GitHub Actions apuntando a AWS, o los servicios propios:

  • CodeCommit — repos Git gestionados.
  • CodeBuild — compila y corre tests.
  • CodeDeploy — despliega a EC2, ECS o Lambda (rolling, blue-green).
  • CodePipeline — orquesta las etapas anteriores.

Para que el pipeline hable con AWS sin claves largas: OIDC entre GitHub Actions y un rol IAM.

12. Observabilidad

  • CloudWatch: métricas, logs, alarmas y dashboards. El centro de todo.
  • CloudTrail: registro de quién llamó a qué API y cuándo. Auditoría y forense. Activalo en todas las regiones.
  • X-Ray: trazas distribuidas: seguir una request por todos los servicios.
  • AWS Config: historial del estado de configuración de cada recurso y reglas de cumplimiento.

13. Seguridad

Además de IAM bien hecho:

Servicio Para qué
KMS Gestión de claves de cifrado. Cifrá S3, EBS, RDS, secretos.
Secrets Manager Guardar y rotar credenciales, tokens, cadenas de conexión. (Parameter Store es la alternativa más simple y barata.)
GuardDuty Detección de amenazas: analiza CloudTrail, DNS y flujos de red buscando actividad rara.
Security Hub Tablero central que junta hallazgos y chequea contra estándares (CIS, AWS FSBP).
WAF / Shield Firewall de aplicaciones web y protección anti-DDoS delante de CloudFront/ALB.
Inspector Escaneo de vulnerabilidades en EC2, imágenes de ECR y Lambda.

Reglas de oro: cifrado en reposo y en tránsito por defecto, nada de buckets públicos, CloudTrail siempre encendido, y raíz con MFA y sin claves de acceso.

14. Control de costes

  • AWS Budgets: alertas cuando el gasto proyectado supera un umbral.
  • Cost Explorer: ver en qué se va la plata, por servicio y etiqueta.
  • Pricing Calculator: estimar antes de desplegar.
  • Etiquetá todo (Project, Env, Owner) para poder filtrar el gasto.
  • Lo que más sorprende en la factura: NAT Gateway, tráfico de salida a internet, EC2 y RDS encendidas sin usar, snapshots viejos, IPs elásticas sin asociar.
  • Ahorro: Savings Plans / Reserved Instances para carga estable; Spot para trabajos tolerantes a interrupción.

15. Well-Architected Framework

La guía de AWS de cómo debería estar hecha una arquitectura, en seis pilares. Vale la pena leerla entera: Well-Architected.

  1. Excelencia operativa — automatizar, medir, mejorar.
  2. Seguridad — mínimo privilegio, trazabilidad, cifrado.
  3. Fiabilidad — recuperarse de fallos, escalar horizontalmente.
  4. Eficiencia del rendimiento — usar el servicio adecuado al problema.
  5. Optimización de costes — no pagar de más.
  6. Sostenibilidad — minimizar el impacto ambiental.

Ruta de aprendizaje recomendada

  1. Crear la cuenta, asegurar la raíz, poner un Budget.
  2. IAM: usuarios, grupos, roles y políticas. Practicar mínimo privilegio.
  3. Instalar la CLI y hacer todo desde ahí en paralelo a la consola.
  4. Levantar una EC2 en una VPC propia, con su Security Group, y entrar por SSH.
  5. Servir un sitio estático desde S3 + CloudFront.
  6. Una app web chica: EC2 o Elastic Beanstalk + RDS, o bien API Gateway + Lambda + DynamoDB.
  7. Meter todo lo anterior en CloudFormation o Terraform y recrearlo desde cero.
  8. Añadir un pipeline (CodePipeline o GitHub Actions) que despliegue en cada push.
  9. Sumar CloudWatch (alarmas), CloudTrail y un Budget con alertas.
  10. Repasar los seis pilares del Well-Architected sobre lo que construiste.

Después de esto, el examen AWS Solutions Architect Associate (o Cloud Practitioner si querés algo más liviano primero) queda a tiro.
