Jenkins

Guía práctica para aprender a usar Jenkins: qué es, cómo instalarlo, y cómo armar pipelines como código con Docker y webhooks.

Qué es

Jenkins es un programa que corre en un servidor y ejecuta comandos por vos cuando pasa algo (por ejemplo, cuando alguien sube código a un repo).

Vos le dejás escrita una instrucción del tipo: "cuando haya un push: bajá el código, compilalo, corré los tests y avisame si algo falló". Jenkins lo hace solo, todas las veces igual, y te muestra el resultado: verde si salió bien, rojo si algo se rompió, con el log completo.

  • CI (Integración Continua): cada cambio se baja, compila y testea automáticamente. Los errores se detectan en el momento, no días después.
  • CD (Entrega / Despliegue Continuo): si los tests pasan, Jenkins empaqueta la app y la despliega a un entorno.

El job (o pipeline)

Un job es una receta: una lista de pasos que Jenkins ejecuta en orden (clonar el repo, compilar, testear, guardar el resultado). Cada ejecución de esa receta es un build, y se numera (#1, #2, #3…). Cada build queda guardado con su log y su resultado.

Instalar (con Docker)

La forma más limpia de probar Jenkins es en un contenedor: cuando terminás lo borrás y no queda nada instalado en tu máquina. Requisito: Docker Desktop abierto y andando.

1. Crear un volumen

El volumen guarda la configuración, los jobs y el historial. Sin volumen, cada reinicio del contenedor borra todo. 

docker volume create jenkins_home

2. Levantar Jenkins

docker run --name jenkins -d \
  -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts-jdk21
PartePara qué
--name jenkinsNombre del contenedor (para parar / borrar)
-dCorre en segundo plano
-p 8080:8080La interfaz web, en localhost:8080
-p 50000:50000Canal para los agentes que se conectan
-v jenkins_home:/var/jenkins_homeGuarda la config en el volumen
jenkins/jenkins:lts-jdk21Imagen: versión estable (LTS) con Java 21

3. Contraseña inicial

Esperá medio minuto a que arranque y corré:

docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword

4. Configurar en el navegador

  1. Abrí http://localhost:8080
  2. Pegá la contraseña inicial
  3. Elegí "Install suggested plugins" y esperá
  4. Creá tu usuario admin

Otras formas de instalarlo

Además de Docker, Jenkins se distribuye como un .war de Java (java -jar jenkins.war) y como paquete nativo de cada sistema (Debian/Ubuntu, RedHat, Windows como servicio). Todas guardan sus datos en un directorio llamado JENKINS_HOME (en el contenedor es /var/jenkins_home): ahí viven la config, los jobs, el historial y los plugins. El ejecutable de Jenkins se puede reinstalar o actualizar sin tocar ese directorio.

Es la pantalla principal: la lista de jobs (todavía vacía), la cola de builds y el estado general. "New Item" crea un job nuevo.

Configurar Git

La imagen de Docker ya trae git. Si usás otro sistema, en Manage Jenkins → Tools le decís a Jenkins dónde están las herramientas. Para builds de Java necesitarías configurar un JDK ahí; para Node, el plugin de NodeJS; etc.

Primer pipeline

Hay dos formas de definir un job: Freestyle (llenando formularios en la web) y Pipeline (escribiendo la receta como código). Hoy se usa Pipeline: queda versionado en el repo y es más fácil de revisar y reutilizar.

Crear el job

  1. Dashboard → New Item
  2. Nombre, elegí Pipeline, OK
  3. Bajá a la sección Pipeline
  4. En "Script", pegá el pipeline de abajo, Save

El pipeline mínimo

pipeline {
    agent any
    stages {
        stage('Saludar') {
            steps {
                echo 'Hola desde Jenkins'
            }
        }
    }
}
  • pipeline { } — todo el pipeline va acá adentro.
  • agent any — ejecutá esto en cualquier máquina disponible.
  • stages { } — la lista de fases.
  • stage('Saludar') { } — una fase, con nombre.
  • steps { } — los comandos de esa fase.
  • echo — imprime un texto en el log.

Correrlo y mirarlo

Build Now. Después, en la página del build:

  • Console Output — el log completo. La línea + echo Hola… es el comando; abajo, su salida.
  • Stage View (página del job) — las fases en columnas, con el tiempo de cada una.
  • Build History — #1, #2, #3… cada corrida guardada.

Pipeline de verdad

Cada paso: cambiás el pipeline, Build Now, mirás qué pasó.

Que un stage falle

stage('Test') {
    steps { sh 'exit 1' }
}

Resultado: Test se pone rojo, los stages siguientes no corren (Jenkins frena en el primer fallo), el build queda rojo. Eso es CI: un test roto detiene todo antes de deployar.

Hacer algo real (no echo)

stage('Build') {
    steps {
        sh '''
            echo "Compilando..."
            mkdir -p salida
            echo "app v1.0" > salida/app.txt
            cat salida/app.txt
        '''
    }
}

sh corre shell de Linux (el contenedor es Linux); en un agente Windows sería bat. '''…''' son varias líneas. Eso crea salida/app.txt en el workspace (la carpeta donde este job trabaja). Reemplazás los echo por lo tuyo: mvn package, npm ci && npm test, etc.

Guardar un artefacto

stage('Deploy') {
    steps {
        sh 'echo desplegando...'
        archiveArtifacts artifacts: 'salida/app.txt'
    }
}

Después del build aparece "Build Artifacts" con app.txt para descargar.

Variables y condicionales

pipeline {
    agent any
    environment {
        VERSION = '1.0.3'
    }
    stages {
        stage('Build') {
            steps { sh 'echo "Compilando version $VERSION"' }
        }
        stage('Deploy') {
            when { branch 'main' }        // solo deploya en la rama main
            steps { sh 'echo desplegando...' }
        }
    }
}
  • environment { } — variables para todo el pipeline, se usan como $VERSION.
  • when { } — el stage corre solo si se cumple la condición.

El bloque post

    post {
        success { echo 'BUILD OK' }
        failure { echo 'BUILD ROTO' }
        always  { sh 'rm -rf salida' }   // corre siempre: limpieza
    }

Va después de stages, al mismo nivel. Se ejecuta según cómo terminó el pipeline. Es el lugar para notificar cuando rompe.

Parámetros

    parameters {
        choice(name: 'ENTORNO', choices: ['dev', 'staging', 'prod'])
        booleanParam(name: 'CORRER_TESTS', defaultValue: true)
    }

Después del primer build el botón pasa a ser "Build with Parameters": te pregunta antes de correr. Se usan como ${params.ENTORNO}.

Cuándo arranca (triggers)

Un trigger es lo que dispara el job. Los principales:

Por horario (cron)

triggers {
    cron('H 2 * * *')       // todas las noches ~2:00
}

La H significa "una hora al azar dentro de ese rango", para repartir la carga entre jobs.

Poll SCM

triggers {
    pollSCM('H/5 * * * *')  // revisa el repo cada 5 min; si hay cambios, build
}

Funciona pero es ineficiente (pregunta cada 5 min aunque no haya nada). Mejor el webhook.

Webhook desde GitHub (lo que se usa)

  1. En el job, activá "GitHub hook trigger for GITScm polling".
  2. En el repo de GitHub: Settings → Webhooks → Add webhook.
  3. Payload URL: http://TU-JENKINS/github-webhook/
  4. Content type: application/json.

Ahora cada git push le avisa a Jenkins y el build arranca a los segundos. (Si Jenkins corre en tu compu, GitHub no lo alcanza; para probar webhooks necesitás Jenkins en un servidor accesible o un túnel tipo ngrok.)

El Jenkinsfile en el repo

Tener el pipeline pegado en la web de Jenkins tiene problemas: nadie lo ve, no está versionado, y si se rompe el servidor lo perdés. La solución es un archivo Jenkinsfile en la raíz del repo, con el mismo contenido.

Conectarlo

  1. Creá Jenkinsfile en la raíz del repo, pegá el pipeline, commit + push.
  2. En la config del job → "Definition" elegí "Pipeline script from SCM".
  3. SCM: Git → URL del repo → rama.
  4. Script Path: Jenkinsfile.

Ahora la receta vive con el código: queda en el historial de Git, cualquiera la revisa en un PR, y si cambiás de servidor Jenkins se la lleva el repo.

Multibranch Pipeline

En vez de un job por proyecto, creás un Multibranch Pipeline apuntando al repo. Jenkins recorre las ramas: cada rama que tenga un Jenkinsfile se convierte en su propio pipeline, y cada Pull Request también. Un push a una rama dispara solo el pipeline de esa rama.

Tests y reportes

Si el pipeline solo compila, lo único que te dice es "compila". Un montón de código roto compila perfecto. Los tests convierten "compiló" en "probablemente funciona".

Publicar resultados de test

Tu build de tests genera archivos XML (JUnit, surefire, pytest --junitxml, etc.). Le decís a Jenkins que los lea: 

stage('Test') {
    steps { sh 'mvn test' }
    post {
        always {
            junit '**/target/surefire-reports/*.xml'
        }
    }
}

Con eso, la página del build muestra cuántos tests pasaron / fallaron, cuáles fallaron y desde cuándo, y un gráfico de tendencia a lo largo de los builds. Si un test falla, el stage y el build se ponen rojos.

Cobertura de código

La cobertura indica qué porcentaje del código se ejecuta durante los tests: sirve para encontrar zonas sin probar. Tu build la genera (JaCoCo, Cobertura) y un plugin la publica. Podés poner un umbral mínimo: si la cobertura baja de, por ejemplo, 50%, Jenkins marca el build como unstable (bola amarilla) y avisa.

La cobertura es un medio, no un fin: no se trata de subir el número porque sí, sino de detectar código sin testear y agregarle tests.

Verde / amarillo / rojo

ColorSignifica
Verde (o azul)Build OK: compiló y pasó los criterios de calidad
AmarilloUnstable: compiló pero falló algún test o quedó bajo un umbral
RojoFailed: el build no llegó a terminar (error de compilación, comando que falló)

Comandos útiles del contenedor

docker logs -f jenkins        # ver el log en vivo
docker stop jenkins           # apagar
docker start jenkins          # prender otra vez
docker restart jenkins        # reiniciar
docker exec -it jenkins bash  # entrar al contenedor
docker rm -f jenkins          # borrar el contenedor (el volumen sigue)
docker volume rm jenkins_home # borrar la config también (todo)
  • La config, los jobs y el historial viven en /var/jenkins_home dentro del contenedor, que es el volumen jenkins_home.
  • Mientras no borres el volumen, podés borrar y recrear el contenedor todas las veces que quieras sin perder nada.
  • Backup: hacer copia del volumen (docker cp jenkins:/var/jenkins_home ./backup).
  • Limpiar builds viejos: en el pipeline, options { buildDiscarder(logRotator(numToKeepStr: '20')) } guarda solo los últimos 20.
